# Runtime 关闭边界与取消后重试

日期：2026-10-29。源码基线 `3132c6c`；本批只修复既有生命周期契约，不增加能力、依赖、存储 Schema 或执行权威。原 a8 制品、manifest 和全部历史验收／失败保持。

## 已复现问题

1. **P2：缓存的可选端口绕过 RuntimeInstance 关闭保护。** `__getattr__` 仅为固定基础方法包装生命周期检查。真实工具线程使异步关闭停留在排空阶段时，预先缓存的 `send_input`、`patch_plan` 或 `compact_messages` 仍能写入命令；四个可选观察方法也能返回结果，与已有关闭契约不符。取消外层关闭等待不会结束真实工具线程，不能据此恢复业务访问。
2. **P2：资源台账可被清理回调重入或被多个调用共同消费。** 同步 `close()` 回调重入 Context／Runtime，会再次进入同一资源的关闭；两个 Context 异步清理调用则可能同时等待同一资源 Task，并分别执行出栈。既有异步资源 Task 的自重入检查不能覆盖同步回调和其他调用方。

## 最小修复与范围

- 将七个已有可选控制／观察方法加入原 RuntimeInstance 的保护集合，保持签名、正常开放状态、原 Engine 和受理契约。关闭后的业务续接通过新实例和原数据库／Profile 进行，原关闭实例只重试清理。
- 原 BuildContext 的同步与异步清理共用机械性重入保护；只阻止第二个调用消费同一台账，不新增资源管理器或执行状态机。外层失败／取消时释放当前清理调用的保护；原异步资源 Task、未关闭资源和真实线程责任仍按原机制保留。
- 资源回调未捕获重入拒绝时，当前资源留在栈上；显式重试只重试该未完成资源，已经完成的资源不再关闭。原 busy-close 拒绝后的取消能力、共享 Host 所有权和资源创建循环保持。
