# 旧编排崩溃测试：10 秒超时定位与整轮复验

日期：2026-11-04。源码基线 `1c5bd4777b771f536cbc23e764cb4b0cb2bc2e09`。用户授权定位并修复两项旧超时，保持原期限和恢复契约，保留失败记录；完成后仅本地提交，单次跳过钩子，不推送或公开发布。本批不扩展框架能力、不重建原制品。基线 `1c5bd47` 已按此前授权推送开发分支；本次测试修复继续仅本地提交。

## 原始问题与证据边界

原[节点批次](2026-11-04-managed-async-nodes.md)的完整离线回归为 15303 passed、895 skipped、8 failed。其中六项 README 链接已在原提交修复，本批关注另外两项：`run_succeeded` 的恢复子进程与 `plan_verified` 的崩溃子进程，均触发原 `subprocess.run(timeout=10)`。此前单文件三轮通过不能替代整轮，也不能证明根因消失。

原异常中的 `stdout_seq=[]` 只说明父进程尚未捕获数据。POSIX 超时路径 kill／wait 后未必排空管道，因此不能仅凭它断定子进程没有写出 `run_id` 或尚未进入 drive。本批用独立阶段文件替代这个推断。

核对原时段的 macOS 电源记录，整轮确实跨越 Idle Sleep、Clamshell Sleep 与 Maintenance Sleep。JUnit 时间至文件结束约 70 分钟，而记录的单调时钟运行时长约 38 分钟，约 32 分钟差额与睡眠记录吻合。这确认了原整轮的连续运行条件受到干扰；**没有历史子进程栈，不能声称已还原两次超时的精确停点，也不能把睡眠或 FD 增长当作已证明的唯一原因**。

另一个可复现的问题是夹具只用 `with sqlite3.connect()` 管理事务，未显式关闭连接。完整诊断前缀的五个 case 后，父 FD 从 44 增至 64，每例增加四个。这个资源所有权问题有确定的 RED，必须修复；它与历史超时的直接因果仍不作推断。

## 最小修复

- 仅测试层新增 session 级 macOS 保活：用标准 `/usr/bin/caffeinate -i -w <pytest PID>` 持有原始 Popen 句柄，独立进程组，退出／中断时 terminate、限时 wait，必要时只 kill 同一句柄再 wait。非 Darwin 不创建进程，守护进程提前消失使会话失败，不静默声称已受保护。未改系统电源设置或 SDK 生命周期。
- 对父进程的持久化证据读取与子进程计数连接增加外层 `closing`；原 SQLite 事务仍在内层，先提交／回滚再关闭。没有改变 SQLite 同步级别、故障点或恢复事实。
- 夹具在导入、Store／Engine 初始化、提交、run_id flush、drive 与关闭处写独立 JSONL；第 8 秒 faulthandler 仅记录线程栈。实际崩溃仍位于已提交事务之后，退出码仍为 77。原 `-m` 命令、每进程 10 秒、一次规划／一次模型调用／两个 Run 的断言全部保留；无预热、重试、延长或跳过。

防空闲睡眠不防强制合盖或显式 sleep。session 保护从首项测试 setup 开始；本批整轮外层只覆盖启动／收集，到 session 自有守护生效后即释放。长回归仍需开盖接电，使用方式见[贡献指南](../../CONTRIBUTING.md)。这不是业务 Run 的取消、deadline 或恢复策略。
